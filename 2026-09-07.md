# Briefing — 7 de setembro de 2026

1. Passkeys chegaram à escala global

A FIDO Alliance reportou, em 7 de maio de 2026, aproximadamente 5 bilhões de passkeys em uso, com 75% dos usuários pesquisados tendo habilitado ao menos uma passkey. FIDO State of Passkeys 2026

Impacto arquitetural: passkeys devem ser tratadas como caminho principal no ChappiePass, não apenas como MFA posterior ao link do WhatsApp. O WhatsApp pode continuar funcionando como canal de descoberta, confirmação e recuperação, enquanto a passkey fornece a autenticação criptográfica resistente a phishing.

Follow-up: medir separadamente:

- criação de passkey;
- login via passkey;
- recuperação após perda do dispositivo;
- sincronização entre dispositivos;
- remoção/revogação de credenciais.

2. Portabilidade de credenciais continua sendo um ponto crítico

O ecossistema FIDO continua avançando no Credential Exchange Protocol/Format para permitir transferência segura de passkeys entre provedores de credenciais, mas essa área ainda deve ser tratada como evolução de interoperabilidade, não como dependência obrigatória. FIDO Credential Exchange discussion

Impacto: o ChappiePass não deve depender exclusivamente de uma passkey sincronizada por Apple, Google ou outro gerenciador. O modelo precisa manter múltiplos autenticadores registrados, revogação granular e recuperação pelo vínculo WhatsApp + prova adicional.

Follow-up: testar perda de telefone, troca de sistema operacional, restauração de backup e migração entre gerenciadores.

3. DPoP está se expandindo para fluxos além do login web

Além do RFC 9449, surgiram propostas para usar DPoP em Device Authorization Grant e para separar as chaves de access token e refresh token. Essas propostas ainda são drafts, mas são diretamente relevantes para um fluxo WhatsApp-first em que um dispositivo inicia a autenticação e outro dispositivo confirma. RFC 9449, DPoP para Device Authorization Grant, DPoP-RT draft

Impacto: vale separar:

- chave de identidade/autenticação;
- chave de sessão;
- chave de access token;
- chave de refresh token.

Isso combina bem com o ChappiePass: o link enviado pelo WhatsApp pode autorizar uma transação específica, sem se tornar um bearer token reutilizável.

Follow-up: implementar testes de replay, roubo de token, rotação de chave, nonce, troca de dispositivo e refresh em contexto diferente.

4. mTLS permanece adequado para serviço-a-serviço, não para o usuário final

O RFC 8705 continua definindo mTLS e tokens vinculados a certificados para autenticação de clientes OAuth. RFC 8705

Impacto: mantenha a separação arquitetural:

- passkey/WebAuthn para autenticação humana;
- DPoP para vincular sessões e tokens de clientes/dispositivos;
- mTLS para comunicação entre gateways, agentes, Actors e serviços internos.

Usar mTLS diretamente no fluxo do usuário móvel criaria complexidade operacional desnecessária de certificados, renovação e recuperação.

Follow-up: validar como o certificado do cliente atravessa proxies e terminadores TLS, e garantir que a identidade mTLS não seja confundida com a identidade humana autenticada pela passkey.

5. A migração pós-quântica já deve começar

O NIST recomenda iniciar a migração para os padrões finalizados FIPS 203, 204 e 205: ML-KEM, ML-DSA e SLH-DSA. O NIST também selecionou HQC para padronização adicional em março de 2025. NIST PQC, FIPS PQC standards

Impacto: a prioridade do ChappiePass não é substituir WebAuthn imediatamente por PQC — o ecossistema WebAuthn ainda depende amplamente de algoritmos clássicos e suporte de plataforma. A prioridade é tornar o sistema crypto-agile:

- versionar algoritmos e formatos de chave;
- permitir certificados mTLS híbridos ou substituíveis;
- preparar ML-KEM para proteção de canais e envelopes;
- evitar formatos de sessão acoplados a Ed25519/X25519 para sempre;
- registrar qual algoritmo protege cada credencial e evento.

Follow-up prioritário da semana: criar uma matriz de criptografia do ChappiePass com algoritmo, finalidade, ciclo de rotação, dependência de plataforma e estratégia de migração PQC.

Síntese

A decisão arquitetural mais importante é consolidar três vínculos distintos:

WhatsApp = canal de interação e recuperação
Passkey = prova de identidade humana
DPoP/mTLS = prova de posse e confiança entre componentes

O próximo teste de maior valor é um cenário completo de troca de dispositivo: autenticação iniciada no navegador, confirmação pelo WhatsApp, passkey em um segundo dispositivo, emissão de token DPoP, comunicação mTLS interna e recuperação após revogação do dispositivo original.
