# Briefing — 5 de outubro de 2026

Há uma mudança relevante no WebAuthn e uma linha de evolução particularmente interessante para sua arquitetura agentic. DPoP e mTLS tiveram menos mudanças normativas recentes.

1. WebAuthn Level 4 começou oficialmente

Em 15 de setembro, o W3C publicou o primeiro Working Draft público do WebAuthn Level 4. Isso acontece poucas semanas depois de o Level 3 ter se tornado uma Recommendation oficial, em 25 de agosto. 

O ponto arquitetural importante é a separação entre os dois:

- WebAuthn L3 agora é uma base normativa estável para implementar o ChappiePass.
- L4 é o espaço para acompanhar novas capacidades; ainda não deve virar dependência de produção.

O L4 continua reforçando o modelo de credenciais públicas fortes, scoped e attested, com o user agent mediando o acesso ao autenticador e o autenticador fornecendo prova criptográfica de suas propriedades. 

Impacto para o ChappiePass: este é um bom momento para congelar seu contrato interno de WebAuthn contra L3, em vez de esperar pela evolução da especificação.

Recomendação:

WebAuthn L3 → Authentication Proof → Intent Authorization

e não:

WebAuthn → sessão autenticada → autorização irrestrita

Isso preserva a possibilidade de incorporar capacidades de L4 posteriormente sem alterar o modelo de identidade.

2. A direção da FIDO está convergindo com seu conceito de Human-Agent-to-Human

A própria FIDO está colocando agentic authentication como uma das próximas fronteiras: a conferência Authenticate 2026, marcada para 19–21 de outubro, destaca explicitamente a necessidade de garantir que humanos verificados estejam por trás de agentes de IA que atuam em seu nome. 

Isso é particularmente relevante para seu modelo.

A arquitetura não deveria terminar em:

Human → Passkey → Agent

mas em:

Human → Passkey → Intent → Agent → Action

com a possibilidade de o agente precisar demonstrar posteriormente:

"qual humano autorizou esta ação?"

Isso torna seu IntentID, ActorID, BehaviorID e trajetória de autorização muito mais importantes que simplesmente manter uma sessão autenticada.

Follow-up: vale formalizar uma credencial de delegação que carregue, no mínimo:

HumanID + AgentID + IntentID + Scope + Audience + Expiry + Nonce

e que seja distinta tanto da passkey quanto do token de acesso do agente.

3. DPoP continua sendo especialmente interessante para autorização entre agentes

Não apareceu uma nova RFC DPoP nesta janela, mas existe uma evolução importante no próprio ecossistema OAuth: há trabalho para aplicar proof-of-possession a contextos além do HTTP tradicional, além da proposta de DPoP para Device Authorization Grant. 

Isso se encaixa diretamente no seu cenário de WhatsApp-first.

O fluxo pode ser pensado como:

WhatsApp
   ↓
Human confirmation
   ↓
WebAuthn
   ↓
Intent authorization
   ↓
DPoP-bound token
   ↓
Agent
   ↓
Action

A vantagem é que o token não representa simplesmente "este usuário está logado". Ele representa uma autorização vinculada a uma chave que o executor precisa possuir.

Follow-up: não trate DPoP como autenticação humana. Use-o como camada de proof-of-possession da autorização delegada.

4. mTLS está evoluindo na direção de workload identity + OAuth

Um draft de setembro propõe um perfil X.509 para OAuth que permite que workloads que já possuem certificados curtos, como SPIFFE/SPIRE, usem esses certificados diretamente para solicitar tokens OAuth. O draft exige prova de posse da chave privada correspondente, evitando que somente a cópia do certificado seja suficiente. 

Isso é bastante próximo da separação que você vem desenhando:

mTLS = quem é o workload

DPoP = quem possui a chave da autorização

WebAuthn = quem é o humano

Intent = o que foi autorizado

Eu manteria exatamente essa separação, em vez de tentar fazer um único mecanismo representar todas as identidades.

5. PQC: a prioridade continua sendo crypto-agility

Não surgiu nesta semana uma nova alteração nos padrões PQC finalizados do NIST. O NIST continua recomendando a migração para seus padrões finalizados e confirma que ML-KEM e ML-DSA permanecem prontos para implementação; a retirada do HAWK após a vulnerabilidade descoberta em julho não afeta esses padrões. 

Para sua arquitetura, isso reforça uma decisão importante: não acople Identity, Credential, Token ou Event a uma primitiva criptográfica específica.

Especialmente no seu caso, eu evitaria algo como:

UserCredential {
    algorithm: "Ed25519"
}

como contrato arquitetural permanente.

Prefira algo conceitualmente equivalente a:

Credential {
    scheme
    algorithm
    public_key
    version
    valid_from
    valid_until
}

permitindo evolução para combinações híbridas e futuras primitivas sem modificar a semântica da identidade.

O que merece ação agora

A prioridade desta semana não é trocar criptografia. É consolidar o modelo de delegação verificável de intenção.

A arquitetura mais interessante para seu sistema começa a ficar:

HUMAN
                    │
              WebAuthn L3
                    │
             Human Proof
                    │
              IntentID + Scope
                    │
             Delegation Proof
                    │
              DPoP-bound token
                    │
                  AGENT
                    │
                mTLS/X.509
                    │
                WORKLOAD
                    │
                 ACTION

E o sistema deve conseguir reconstruir a cadeia:

Human → Intent → Delegation → Agent → Workload → Action

Essa cadeia é mais importante para o seu projeto do que simplesmente ter "passwordless login". A evolução do WebAuthn para L3 estável e a crescente discussão sobre autenticação de agentes tornam esse modelo especialmente oportuno agora.
